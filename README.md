# notyas

notyas is an airgapped Bitcoin signer that runs on off-the-shelf ESP32-P4 touch panels. You
roll physical dice or type a mnemonic you already have; the device derives the seed and the
public keys under it. On a board whose eFuse device key has been provisioned it can also set
a PIN, seal a wallet into flash so it survives a power cycle, register a multisig wallet, and
take a PSBT off a microSD card, review it, and sign it from the panel.

It hands out native segwit addresses by default, and it signs all four single-sig script
types it derives: BIP-84 native segwit, BIP-86 taproot, BIP-49 wrapped segwit and BIP-44
legacy. It also signs k-of-n P2WSH `sortedmulti`, up to fifteen cosigners, from a
registration it has proved it is a member of.

No radio, no network stack and no USB data path is compiled into the image, and the
transaction path is a microSD card rather than a cable. What that does and does not buy on
this silicon is the next section, not a footnote. Free software under the GNU GPL, version 3
or later.

## Status and safety - read this first

**This is preview firmware for testing. Do not put real funds behind a seed generated by
it.**

- **No independent security audit has been performed on this code.** None is claimed.
- **No Secure Boot v2, no flash encryption, no eFuse anti-rollback, no JTAG or
  download-mode lockdown.** The one eFuse this firmware's provisioning ceremony burns is
  the HMAC key the sealed store binds to. An attacker who gets the device powered with a
  USB cable attached can halt the cores over the USB-Serial-JTAG peripheral or rewrite the
  app partition through ROM download mode. [docs/SECURITY.md](docs/SECURITY.md) states this
  in full under "The powered device". It is the cheapest attack on this hardware and
  nothing here closes it.
- **No secure element.** The ESP32-P4 has none and notyas does not add one. There is no
  tamper-resistant key storage on this device. What the eFuse binding buys is that every
  PIN guess costs the attacker this physical board. It does not make a 4-digit PIN survive
  an attacker who has extracted the eFuse key, and a consistent full-flash snapshot and
  restore is neither detectable nor preventable.
- **Nothing on the device checks the firmware**, so every value the Verify screen shows is
  the running firmware reporting on itself. That detects corruption, and it lets you
  compare a unit against a digest you produced yourself; it cannot prove the firmware is
  the firmware you think it is. See "The self-reporting boundary" in docs/SECURITY.md.
- **The firmware has run on two of the ten boards it has modules for.** The other eight are
  source-verified scaffolds that have never run on hardware.
- **The on-device signing loop has never been driven from a touch panel.** The screens, the
  card subsystem and the signing engine are wired together in `firmware/src/flow/` and
  covered by host tests; nobody has yet sat in front of a device and taken a PSBT from card
  to signature that way. What has run on hardware is the same engine driven over the
  development console, on a board that is not eFuse-provisioned
  ([docs/clause2-evidence.md](docs/clause2-evidence.md)). "What has never been run on a
  device" below says which steps that leaves unproven.
- **The dev boards ship with Secure Boot and flash encryption off.** The Verify screen
  reports their true state; it does not pretend they are on.

Use it against testnet, against published test vectors, and against a seed you are prepared
to throw away.

## Two ways in

A device with nothing saved opens on a menu offering "New seed (dice)", "Verify existing
seed" and "Verify device". Nothing is written unless you choose to write it. A device that
has saved a wallet opens "Locked", and the PIN is the way in: a wrong PIN costs an attempt,
and at the configured threshold the device erases what it has stored.

| | | |
|---|---|---|
| ![A device with nothing saved](docs/screenshots/ui/01-home.png) | ![Locked](docs/screenshots/ui/16-lock.png) | ![The wallet list](docs/screenshots/ui/136-wallet-list-one.png) |
| A device with nothing saved: the menu is the way in | A device that has saved a wallet opens "Locked" | After the PIN: "Wallets", and what the device is holding |

Past the entrance both routes run the same screens - dice entry, the words behind a two-step
reveal, the optional passphrase, and a word-by-word backup check that is never skipped - and
both end at the same question: "Save to this device" or "Use once, keep nothing". That is
the one place anything is written, and it comes after the backup check with the words in
front of you. "Use once, keep nothing" ends on a "Session wallet" that hands out public keys
and addresses and is gone at power-off. "Save to this device" sets a PIN first if the device
has none, and puts the wallet in a slot, where "Wallets" lists it after every power-on. The
"Lock device" chip in the top bar is the way back to "Locked".

A card on the lock screen reaching dice entry without a PIN is specified in
[docs/plan-0.2.0/SIMPLE-MODE.md](docs/plan-0.2.0/SIMPLE-MODE.md) and is not in this build.

[docs/TOUR.md](docs/TOUR.md) walks all of it, function by function, with recordings.

## What a unit does

Everything here is reachable from the panel in a build with no development features
compiled in.

**Making or restoring a wallet**

- **Dice entry** with a running effective-bits count and roll history, in six modes: RAW (a
  prefix-free variable-length base-6 code) and fixed 12/15/18/21/24-word.
- **Mnemonic display** behind a two-step reveal gate, masked by default, followed by a
  word-by-word backup check before anything else is offered.
- **Restore by typing a mnemonic**, with BIP-39 autocomplete, a checksum verdict and a
  final-word helper.
- **Optional BIP-39 passphrase**, with an explicit opt-in, a Show/Hide toggle and an NFKD
  byte counter.

**Seeing and handing out keys**

- **BIP-32/44/48/49/84/86 derivation**: an origin-carrying output descriptor, the account
  xpub, the SLIP-132 form where the scheme has one, and the first receive addresses.
- **Receive**: one address at a time with its QR, the derivation named underneath it
  (`BIP-84 native segwit - m/84'/0'/0'/0/0`), a Next button, and a Save to SD that writes
  `receive-address.txt` through the same staged, read-back, collision-checked write path
  every other card write uses.
- **Export**: one tab per scheme, opening on BIP-84. Each tab leads with the descriptor,
  then the bare account xpub, then the SLIP-132 form where the scheme has one, then the
  address rows. Every block has a QR button and every payload is a public value. Which
  block to hand your coordinator, and why the choice matters, is
  [its own section below](#setting-up-a-coordinator-hand-it-the-descriptor).

**Storing a wallet, on a provisioned board**

- **Set a first PIN and seal a wallet.** The create flow offers keep-in-session or save;
  the save path formats the sealed store under a PIN typed twice, and the wallet is sealed
  into the lowest free slot.
- **Unlock and open a stored wallet** after a power cycle, with anti-phishing words at
  half-PIN entry derived from the eFuse key, an attempt counter, and a wallet list.
- **Store or forget a passphrase** in a wallet's sealed record. Storing is opt-in behind a
  consequence sheet; forgetting is behind a hold sheet. A wallet whose record carries no
  passphrase asks for one at unlock, and a wrong one produces a refusal that states
  derivation facts rather than a verdict.
- **Delete a stored wallet**, behind a consequence sheet, a typed-name sheet, and a final
  offer of the recovery words. The device erases the payload record and that wallet's
  registrations, then reads the slot back and reports `Gone`, `Refused` or `Damaged` from
  what the flash actually holds rather than from the fact that a write returned
  (`firmware/src/wallet/erase.rs`).
- **Name the device**, which is what the lock screen shows.

**Signing**

- **Mount and browse a microSD card** from the sign-source and multisig-import screens: a
  bounded catalog, directories, and a file picker that never looks inside a file.
- **Load a PSBT off the card and review it.** The file is read under a cap, its wrapper is
  sniffed (BIP-174 binary, ASCII hex, or base64), it is decoded, and it goes through the
  ten-check validation pipeline **with no signing key in scope**, so every refusal happens
  before any spending authority exists. The review pages state the inputs, the outputs, the
  totals and the fee, together with whether that fee is enforced by proven amounts or
  merely claimed by the file.
- **Sign it**, with a hold gesture that only exists once every review page has been
  visited. Every signature the device produced is then re-verified against a sighash
  recomputed from the PSBT alone, before the file is released.
- **Write the signed transaction back to the card** as `<name>-signed.psbt`, under a name
  the panel showed before the write happened, with a name collision asked about rather than
  resolved. Or **show it as a QR**: one static symbol, for a signed transaction of 1089
  bytes or less. Over that the control is drawn disabled with both numbers on it, because
  1089 bytes is the most a version 31 symbol at level M carries at a module size the
  shortest shipped panel can still draw (`crates/notyas-core/src/psbt_qr.rs`,
  `MAX_PSBT_BYTES`). Or **discard it**, which destroys the only copy this device holds.
- **Import and register a k-of-n P2WSH `sortedmulti` wallet**, up to 15 cosigners, from a
  descriptor or a Coldcard setup file on the card. The device proves it is a member of that
  wallet, from the seed, before any screen renders it; a wallet it cannot sign for is
  refused at import. Registrations can be listed, inspected cosigner by cosigner, and
  deleted.

**Checking the device**

- **Verify device**: firmware version, board, IDF and silicon revision, SHA-256 of the
  running app partition, source-id hash, boot self-test result, radio-kill pad readback,
  eFuse HMAC-key state, the three secure-boot digest slots, flash-encryption and
  download-mode fields, boot count, and a deliberately coarse storage state. Every field is
  read at boot and none of them is a compiled-in constant.
- **A boot self-test** of the crypto core, eleven checks (`CHECK_COUNT` in
  `crates/notyas-core/src/selftest.rs`), run before the display, the touch controller and
  the card subsystem come up. Two things do touch hardware before it, both deliberately:
  `board::radio_lockdown()` drives the radio-kill line as the first thing `main` does, and
  the sealed store is mounted, which reads flash and may program one boot cell so that a
  boot ending on the failure screen is still counted (`firmware/src/main.rs`). The firmware
  refuses to present a normal UI if any check fails.

Export and Receive need only the derivation that is on the screen. **Sign and Multisig are
offered only on a wallet that came out of a slot**, because the only seed the firmware ever
holds is one it unsealed: a keep-in-session wallet hands the screens a derivation and hands
the firmware no seed. The gate is in `crates/notyas-ui/src/screens/wallet.rs`, and a
stateless signing entry does not exist. The same menu therefore appears with two, three or
seven actions on it depending on what the device is actually holding;
[the three side by side](docs/TOUR.md#managing-what-is-stored-on-it) is the quickest way to
see which is which.

## What it refuses, and why

This is the part a reader is most likely to meet without warning and read as a broken
device. Every refusal below is deliberate, and each one is either a rule with an attack
behind it or a script type this firmware has no signing arm for.

### A transaction with two or more inputs and any unproven amount

**The rule.** A segwit v0 input may rest on `witness_utxo` alone - the file simply stating
what the coin is worth - in exactly one case: **the unsigned transaction has a single
input.** With two or more inputs, every input's amount must be proven by a full previous
transaction whose txid and output value match, or the file is refused with R-02.

**Why.** A BIP-143 signature binds its own input's amount and no other. In a one-input
transaction there is no second amount for a file to lie about and no second signature for a
later round to combine with, so lying about the only amount invalidates the only signature.
With two inputs a coordinator can prove one amount, merely claim the other, and harvest a
valid signature over the input it proved; then present the same transaction with the roles
swapped and harvest a second. Each round shows an ordinary fee. The two signatures combine
into one transaction that pays far more. This device keeps no chain, no clock, no price and
no history (ratified rule S-35), so it cannot notice the second presentation, and no
stateless rule admits the multi-input case without reopening that attack. The count is
taken over `psbt.unsigned_tx.input`, never over the inputs the device classifies as its
own, because ownership is asserted by the file and a count of "ours" is a count the
coordinator chooses.

**What this costs you in practice.** BlueWallet's PSBT export carries `witness_utxo` and
never `non_witness_utxo`, so a BlueWallet spend of one coin signs and **a BlueWallet
consolidation, or Send Max from a wallet holding more than one UTXO, is refused.** A
cosigner's already-finalized input is not exempt: being finalized says nothing about its
amount.

**The remedy**, which is also what the refusal band says: use coin control to select a
single coin, or rebuild the transaction in software that attaches full previous
transactions - Sparrow, Electrum or Bitcoin Core - and load it again.

Taproot was never affected. BIP-341's `sha_amounts` already binds every claimed amount, so
a taproot input needs no previous transaction and never did.

The reasoning, including the broader relaxation that was implemented, broken with a
two-round test and rejected, is [docs/RELEASE-0.2.1.md](docs/RELEASE-0.2.1.md) section 0.
The rule is pinned in `crates/notyas-core/src/psbt/checks.rs` by
`amount_rotation_over_a_proven_and_a_claimed_amount_is_refused`.

### Legacy inputs are stricter than everything else

A pre-BIP-143 signature commits to **no** input amount, not even its own. The single-input
exemption above therefore never applies to a legacy input: every legacy input's amount must
be proven by a txid-checked full previous transaction, one input or twenty. Legacy signs
under SIGHASH_ALL and nothing else. Sparrow, Electrum and Bitcoin Core all attach previous
transactions, so a file from any of them carries what a legacy input needs.

That rule and its reasoning are [docs/RELEASE-0.2.2.md](docs/RELEASE-0.2.2.md) section 2,
and it is pinned by `a_single_input_legacy_file_may_not_rest_on_a_claimed_amount` and
`a_multi_input_legacy_file_is_refused_at_the_carve_out` in the same `checks.rs`.

### Scripts this device does not sign

An input that claims one of this device's keys, but whose script is neither one of the four
single-sig kinds the signer builds nor a P2WSH a registration can bind, is refused with
R-26, "Not a script this device signs". After legacy signing landed, what reaches it is
P2SH, OP_RETURN and anything unrecognised.

- **A P2SH multisig or P2SH-P2WSH multisig** is refused and there is no remedy in this
  release. They are not script types this device signs.
- **A wrapped-segwit (BIP-49) coin of yours whose redeem script the coordinator left out of
  the file** also lands here, because without the redeem script the input is
  indistinguishable from any other P2SH. That one has a remedy and the refusal names it:
  re-export the transaction with the redeem script included.

### What a refusal looks like on the glass

A refusal is a full screen, not a toast: a code, a headline, "What happened" in the
engine's own words, "Why this matters", and "What to do". The "what to do" line is a
`&'static str` on every code, so a refusal cannot render without an action. "Why this
matters" is optional and is absent on exactly two codes, "No card detected" and "No PSBT
files on this card", because there is no attack behind an empty slot and a fabricated
sentence there would teach a user to skim the section that elsewhere carries the whole
warning.

The codes are R-01 to R-10 for the ten ratified validation checks, R-20 to R-26 for faults
that are not check failures, and R-00 for "this build cannot do that". The full table, with
the exact words each code renders, is [docs/REFUSALS.md](docs/REFUSALS.md).

**Two honest defects in that copy, both open.** Ten refusal rows render text that is false
or misdirected for at least one situation they cover - a previous transaction that is
present and contradicts its input reported as "Missing the previous transaction"; a tamper
tripwire reported as a calm wrong-wallet mixup; an ordinary pre-registration multisig step
reported as a key mismatch. Every one of them refuses the right file for the right reason;
what is wrong is what the user is told to do next. And the engine sentence under an R-26
band still opens "Check 4 (multisig binding)" under a headline that says nothing about
multisig, because the ten-check numbering is ratified and that sentence is what a bug report
is photographed from. Both are tracked in
[docs/KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md).

## What is not in it

- **No finalization.** Nothing in this workspace finalizes a PSBT, so the delivery is
  always a signed PSBT and never a `.txn`. A coordinator finalizes.
- **No way in but the card.** No supported board has a camera. The UR2 and BBQr animated-QR
  codecs in `crates/notyas-wallet/src/transport/` have no screen. A signed transaction can
  go out on the card or as one static QR under the size limit above; an unsigned one can
  only come in on the card.
- **On a Waveshare 4B in its OEM chassis, or in the desk stand this repository ships, the
  microSD slot is unreachable** - it sits behind the backing plate. The only ingress this
  firmware has cannot be used on an assembled 4B; the board runs plate-off
  (docs/KNOWN-ISSUES.md K6).
- **Three sealed-store operations are refused in every build**: commit a wipe-policy
  change, change the PIN, and remove the PIN. Each one re-seals or destroys sealed records
  and needs a fresh confirmation of the PIN, which this UI cannot collect. The screens are
  there and the operations are not. **The consequence to plan around is that the wrong-PIN
  wipe is fixed at fifteen attempts and cannot be raised, lowered or switched off** -
  ["The sealed store, concretely"](#security-model) says why. Two of the three refusals
  reach the user in words, `policy_result(false)` and `pin_removed(false)`; change-PIN has
  no failure channel on `Ui` at all, so its refusal is a log line and the row does nothing
  visible (docs/KNOWN-ISSUES.md K16). (Deleting a stored wallet **is** implemented, and
  reads the slot back before calling itself a delete.)
- **Nothing works on a board that has not been eFuse-provisioned, beyond the stateless
  part.** A release image accepts exactly one key provenance, so an unprovisioned board has
  no store, therefore no PIN, therefore no stored wallet, therefore no Sign action. Such a
  board is a seed tool and public-key exporter, which is a legitimate way to own this
  hardware.
- **No backup of any kind.** Multisig registrations, labels and settings exist only on the
  device and are destroyed permanently by a wipe. Your written-down recovery words are the
  recovery path for the seed and for nothing else. No BSMS. No taproot multisig.
- **The session auto-locks after 120 seconds** with no warning, no countdown and no
  setting, and that has never been exercised against a long review on hardware
  (docs/KNOWN-ISSUES.md K20).
- **The Verify screen's reserved-flash-spans row answers `not read`**, because this build
  has no reader for it. That is the true statement about this image rather than an empty
  result.
- **BIP-85 child keys, BIP-137 signed messages and SeedQR decode** are finished and
  host-tested in `notyas-core` and have no screen. So are the coordinator export bodies -
  generic JSON, Bitcoin Core `importdescriptors`, an Electrum wallet file and an
  address-range CSV, all in `crates/notyas-core/src/export.rs`. The Export screen shows the
  descriptor, the bare xpub, the SLIP-132 form and the address rows, and writes none of
  those files.

| Where | What | Why no screen |
|---|---|---|
| `crates/notyas-core/src/seedqr.rs` | SeedQR and CompactSeedQR decode | No supported board has a camera |
| `crates/notyas-core/src/bip85.rs` | BIP-85 child mnemonics and xprvs | Not designed into this UI |
| `crates/notyas-core/src/message.rs` | BIP-137 signed messages | Not designed into this UI |
| `crates/notyas-wallet/src/transport/` | UR2 and BBQr animated-QR encoding | The out-of-band path this firmware ships is the card |
| `crates/notyas-core/src/export.rs` | Coordinator export files (JSON, Core, Electrum, CSV) | The screen shows text and QR, and writes no export file |

## What has never been run on a device

This section exists because "the code is written, wired and host-tested" and "someone has
watched it work on a device" are different claims, and only the second is evidence. A reader
who has only the first two sections will collapse them, in one direction or the other.

**The whole signing path from the panel has not been driven.** `firmware/src/flow/` routes
`ListCard`, `LoadPsbt`, `SignTx`, `WriteSigned`, `DiscardSigned`, `ImportRegistration`,
`ApproveRegistration` and `DeleteRegistration` into the card and signing modules; the
crate-level dead-code allowance those modules used to sit behind is gone, which is the form
of "it is called now" that a compiler checks. No device has set a PIN from the touch UI,
saved and re-opened a wallet from it, read or written a microSD card in any build, reviewed
or signed a transaction from it, or registered a multisig from it. That is
docs/KNOWN-ISSUES.md K24, open and blocking.

**What has run on hardware, and how.** Create a seed, save it under a PIN, power cycle,
unlock, register a 2-of-3, verify the first receive address, load a PSBT, review it, sign
it, and have Bitcoin Core 29.4 accept the result. That sequence has been run on a board and
is recorded in [docs/clause2-evidence.md](docs/clause2-evidence.md). It was driven **through
the hardware-in-the-loop console, not through the touch UI**, on a build with
`hil-console,unsafe-emulated-key` enabled, on the board that is not eFuse-provisioned, with
the PSBT arriving as a hex string on the console rather than off a card. The panel path
shares the engine with that run and shares none of the wiring between the screens and it.

**Legacy signing is host-tested only.** The two-board hardware pass that is its release gate
is [docs/RELEASE-0.2.2.md](docs/RELEASE-0.2.2.md) section 5 step 5, and it is marked NOT
RUN: the corpus legacy case signed and verified on hardware, the claimed-amount negative
refused on hardware, and a P2SH input claiming our key still refused at check 4.
docs/KNOWN-ISSUES.md K29 does not close until that pass has run on both boards.

**There is exactly one unit the product path can be exercised on at all.** Of the two
verified boards only the Elecrow 5inch has been eFuse-provisioned, and the panel signing
path needs a provisioned board. It has not been.

Sealing is on firmer ground than any of this, and the evidence for it is under
["How this code is tested"](#how-this-code-is-tested) rather than here: an exhaustive host
power-loss proof, a byte-for-byte known-answer test against the real flash driver, and
hand-performed power-cut gates on the provisioned board.

"Untested scaffold" is a hard status, not a soft one: every constant traces to a published
vendor schematic or factory firmware, the module compiles, and that is the entire claim. The
module carries an UNTESTED banner, the firmware logs `UNTESTED BOARD CONFIG` at boot, and
`tools/build.ps1` warns. No hardware of that model has ever run this code.

**Board choice is itself a security choice, and the boards are not equal.** The **Elecrow**
boards pull the C6 EN line high through a 10K resistor, so the radio co-processor boots its
factory firmware at every power-up and runs for a few hundred milliseconds until `app_main`
drives the kill line low. That firmware is not idle during the window: it brings up a WiFi
MAC and a Bluetooth controller, so the device is RF-visible and MAC-identifiable at every
power-on. No build option closes it, because ROM and the second-stage bootloader run before
any code of ours; the mitigations are physical. The **Waveshare** boards carry a C6-MINI
module whose EN has no pullup, so their radio is held down from power-on and the window does
not exist. The Elecrow 5inch additionally carries a socket for LoRa/nRF24/Zigbee modules
that must be physically empty, and an unverifiable STC8 co-MCU on the touch I2C bus that the
backlight requires. Details in docs/SECURITY.md and docs/BOARDS.md.

## Build and flash

This section is for compiling your own image. Installing a published one is
[Putting it on a board](#putting-it-on-a-board) above.

The reference environment is Windows with PowerShell. The firmware needs the ESP-IDF
toolchain; the host crates need nothing but stable Rust.

Prerequisites, one time:

```powershell
rustup toolchain install nightly-2026-07-27 --component rust-src
cargo install ldproxy espflash --locked   # espflash >= 4.5 for the P4
python -m pip install --user libclang     # libclang.dll for bindgen
```

`git` and `python` must be on PATH. `esp-idf-sys` downloads and manages ESP-IDF v5.5.4 and
its toolchains itself on the first build (multi-GB, one time).

Build and flash:

```powershell
tools\build.ps1 -Board waveshare-4b
tools\flash.ps1 -Board waveshare-4b -Monitor

tools\build.ps1 -Board elecrow-5
tools\flash.ps1 -Board elecrow-5 -Monitor
```

`-Board` drives the cargo feature, the sdkconfig pair, the per-board `CARGO_TARGET_DIR`, the
espflash `--flash-size` and the default serial port. The toolchain versions are pinned for
reasons that are not cosmetic - a newer nightly and a newer IDF both currently fail to build
this target - and both boards are pre-v3.0 engineering-sample silicon needing a specific
chip-revision config. **Read [firmware/README.md](firmware/README.md) before your first
build**; it documents the exact versions, the revision trap, and fifteen pitfalls found the
hard way.

To store wallets, provision the board once per [docs/PROVISIONING.md](docs/PROVISIONING.md).
It burns one eFuse key block, host-side, and it is irreversible. Release firmware contains no
eFuse-burn code. Migrating a board that already carries an older partition table is
[docs/SETTINGS-MIGRATION.md](docs/SETTINGS-MIGRATION.md).

Host-side work needs none of the ESP toolchain:

```
cargo test --workspace --exclude notyas-firmware   # the host suite
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo run -p uisim                                 # re-render docs/screenshots/ui/
bash tools/build-graph-check.sh                    # SECURITY.md invariants 1 and 3
```

Plain `cargo clippy --workspace` does not work here: it drags in the firmware crate, and
`esp-idf-sys` rejects an `x86_64-pc-windows-msvc` host target.

## Setting up a coordinator: hand it the descriptor

**Hand your wallet software the descriptor from the top of the Export tab, not the bare
xpub below it.** This is the single most consequential choice in setting the device up, and
the Export screen is ordered the way it is because of it.

A bare extended key is a chain code and a public point. It carries no master fingerprint and
no derivation path, so the coordinator that reads it has to invent both: whose key this is,
and which derivation it came from. BlueWallet's documented default for a bare `xpub` is
legacy `m/44'/0'/0'`.

This is not hypothetical, and it is the reason the Export screen was reordered. A user
loaded a PSBT and was told his cosigner keys did not match. He had no multisig wallet, no
cosigners and no registration; he said so, and he was right. The file was an ordinary
single-sig spend of a coin on his own BIP-44 leaf, and its master fingerprint was
`00000000` - what a watch-only wallet built from a bare account key writes when it has none
to write. The device refused it, correctly at the time, because it had no legacy signing arm
at all, and it refused with the wrong words. Three defaults had put the coins there: Receive
showed the first scheme, which was legacy; Export opened on the legacy tab; and the first
block on every tab was the bare xpub, from which BlueWallet builds a legacy wallet. The
whole report is [docs/RELEASE-0.2.2.md](docs/RELEASE-0.2.2.md) section 0, and all three
defaults and the missing signing arm were closed in that release. The coins were never lost
- the recovery phrase re-derives `m/44'` in any standard wallet - but the only on-device
route out of a legacy coin is legacy signing, and there was none.

The descriptor closes both guesses. It is a BIP-380 output descriptor with a checksum,
carrying this wallet's root fingerprint and the key-origin path in `h` notation:

```
wpkh([a1b2c3d4/84h/0h/0h]xpub6CaWStGvcXqSW.../<0;1>/*)#checksum
```

Per scheme, the device emits `pkh(...)` for BIP-44, `sh(wpkh(...))` for BIP-49, `wpkh(...)`
for BIP-84 and `tr(...)` for BIP-86 (`export::descriptor` in
`crates/notyas-core/src/export.rs`). BIP-48 gets none: a multisig descriptor needs cosigner
xpubs this crate does not accept, and fabricating a `sortedmulti(...)` with placeholder
cosigners would produce a string no coordinator could use.

The fingerprint is the half that keeps mattering after setup. A coordinator that only ever
saw a bare key has none to write, so it writes `00000000` into every PSBT it builds -
indistinguishable from every other signer that got a bare key - and each signer downstream
is left guessing whose key made which signature. That is why the Export screen prints
`DESCRIPTOR_HELP` under the descriptor block and `BARE_KEY_HELP` under the bare one; both
strings are in `crates/notyas-ui/src/screens/schemes.rs` and both name BlueWallet
specifically, because a named guess is checkable and "some wallets may interpret this
differently" is not.

The bare key is still emitted, and still has a QR button, because some coordinators want it
and withdrawing it would break an established workflow. It is simply no longer the first
thing on the screen.

### What each coordinator wants, and what to expect

Hand all four the descriptor. What differs is what comes back. Each statement below about
another project's behaviour is one this repository records rather than one this device has
been driven against, and the three kinds of record are not equally strong. The derivation
rules are written against named upstream implementations: `OwnWallets::prove`'s doc comment
in `crates/notyas-core/src/psbt/checks.rs` names Coldcard's `determine_my_signing_key`,
Electrum's `get_pubkey_derivation` and Sparrow's `Wallet.getSigningNodes`. The BlueWallet
shape is a corpus fixture reconstructed from a field report rather than built from a
captured export, which `crates/notyas-core/src/psbt/fixture.rs` states in its own header.
That Sparrow, Electrum and Bitcoin Core attach full previous transactions is this
repository's own assertion, with no upstream implementation named and no fixture behind it.
The last part of this section says what has actually been exercised.

| Coordinator | What to expect |
|---|---|
| **BlueWallet** | Its descriptor parser reads the fingerprint out of the brackets, which is why `DESCRIPTOR_HELP` names it. Its PSBT export carries `witness_utxo` and never `non_witness_utxo`, so a **one-input** spend signs here and a consolidation or Send Max is refused by the amount rule above. It writes the file as base64 text; this device sniffs that and answers in the same base64. |
| **Sparrow** | Attaches full previous transactions, so multi-input spends carry what this device needs. |
| **Electrum** | Also attaches full previous transactions. When it holds only an account xpub it writes that account key's own fingerprint and a relative `change/index` origin rather than the master's and a full path; this device resolves that spelling on inputs and on outputs. Before 0.2.1 an account-xpub fingerprint was not routed on the output side at all, so a file whose change address had been swapped for the coordinator's reviewed and signed identically to an honest one. That is the defect the ownership rewrite closed, and `electrum_relative_path_stolen_change_psbt` is the fixture that now pins it. |
| **Bitcoin Core** | Also attaches full previous transactions. Import the descriptor with `importdescriptors`. Core is the one external implementation that has judged a file this device signed. |

The device does **not** write a coordinator-specific wallet file to the card. Setup is the
descriptor as text, or as a QR you photograph off the panel, and nothing else. The claims
about Sparrow, Electrum and Bitcoin Core attaching previous transactions are the ones the
R-02 refusal itself names as the remedy, and they are recorded in
docs/RELEASE-0.2.1.md section 0 and docs/RELEASE-0.2.2.md section 4.

### The round trip

1. **Export.** Open the wallet, tap Export, and take the descriptor off the BIP-84 tab -
   read it, or tap its QR button. Build the watch-only wallet in your coordinator from it.
2. **Receive.** Tap Receive to see the next address with the derivation named under it, and
   compare it against the address your coordinator shows for the same index. They must
   match character for character. Save to SD writes it as `receive-address.txt` if you would
   rather compare it on a computer.
3. **Build the spend in your coordinator**, export the PSBT, and put it on a FAT32 card. The
   device reads BIP-174 binary, ASCII hex, or base64, and it never looks inside a file it is
   only listing.
4. **Sign.** Wallet home, Sign a transaction, pick the file. Read every review page - the
   hold gesture that signs does not exist until you have. Amounts the file merely states
   are prefixed `STATED` in words, so the qualifier survives a monochrome photograph.
5. **Take it back.** Write to card produces `<name>-signed.psbt` beside the original, or
   Show as QR puts the whole signed transaction on the glass as one static symbol if it fits
   in 1089 bytes.
6. **Finalize and broadcast in your coordinator.** Nothing in this workspace finalizes a
   PSBT.

### What has actually been exercised against a coordinator

One manual Bitcoin Core 29.4 invocation, over the development console, on the
non-provisioned board: Core computed the same 1,500 sat fee the device displayed, judged the
signature sufficient, and finalized the file
([docs/clause2-evidence.md](docs/clause2-evidence.md), leg 3). One single-sig input, one
file, SIGHASH_ALL, no multisig leg.

**No round trip with BlueWallet, Sparrow or Electrum has been performed on hardware.** What
exists for BlueWallet is a corpus: `crates/notyas-core/src/psbt/fixture.rs` carries the
shape its export takes - `witness_utxo` and never `non_witness_utxo`, a full five-component
derivation path, an all-zero master fingerprint, base64 text under a `.psbt` extension - and
every hostile variant in that group is that file with exactly one field changed, so a
refusal names which fact decided it. `firmware/src/signing.rs` drives the
same file end to end in `bluewallet_base64_export_signs_and_rewraps_in_base64`. That proves
this device handles the shape those wallets produce; it does not prove those wallets accept
what comes back. The external cross-check harness that would put Bitcoin Core and `embit` on
the other side of all 21 corpus cases has never executed (docs/KNOWN-ISSUES.md K25).

## Verifying a release

Every release is signed with one key, unchanged since 0.2.0:

```
A1E9 53B2 5C6A 623B 77A1 D522 3AC4 BBCF E51A B37D
```

The published public half is in
[docs/keys/](docs/keys/A1E953B25C6A623B77A1D5223AC4BBCFE51AB37D.asc), and you should compare
that fingerprint against at least two independent sources rather than trusting the copy in
the repository you are already reading.

[docs/VERIFYING.md](docs/VERIFYING.md) is the verifier-facing guide and it assumes you have
never seen this repository: check a hash, check the signature, rebuild the firmware in a
pinned container, compare it byte for byte with what was published, then compare the
device's own numbers against the per-board manifest. The recipe and its tooling are in
`tools/repro/`; the design behind them is `docs/plan-0.2.0/REPRODUCIBLE.md`.

Read section 1 of docs/VERIFYING.md before you rely on any of it. Without Secure Boot v2, the
Verify screen reports what the running firmware says about itself, so the chain of trust has
to be closed on your own machine: reproduce the published image from published source,
satisfy yourself that the image you flash is that image, and flash it yourself.

**0.2.3 is the first notyas release for which a reproducible-build artifact has ever been
produced, and every release before it has a page with nothing to download.**
`tools/repro/Dockerfile` failed at step 5 of 7 on every attempt that had ever been made, on
GitHub Actions and on every local host, so v0.2.0 and v0.2.2 are tags over gated firmware
that was never packaged: no `app.bin`, no `SHA256SUMS.txt`, no signature over one. Until
this release the procedure above was accurate about the intent and unusable in fact, because
the container it tells you to build could not be built by anybody. The container now runs
all seven steps and `tools/repro/build.sh` runs to `done: <board>`, first proved on
2026-08-23. [docs/RELEASE-0.2.3.md](docs/RELEASE-0.2.3.md) sections 0, 1 and 4 are the
account, and docs/KNOWN-ISSUES.md K34 is the defect entry.

**A second-machine reproduction by an independent party still has not happened.** The recipe
is published and a matching independent build is invited rather than already in hand. Under
the container recipe there are no expected differences: a reproducible build with a section
listing harmless differences is not a reproducible build.

## How this code is tested

**The host suite is one command.**

```
cargo test --workspace --exclude notyas-firmware
```

It runs the official Trezor BIP-39 vectors, iancoleman vectors captured from real JavaScript
executed under node, derivation vectors generated independently by Python `bip_utils`, the
BIP-143/340/341 signing vectors, the adversarial PSBT corpus, the SeedQR vector and fuzz
suites, the multisig vectors including BIP-67 ordering, the sealed-store lifecycle and
tamper suites, a key-material residue check, the structural assertions that no private value
can reach a QR code, and the simulator's graphics gate. docs/RELEASE-0.2.1.md records 1277
tests with zero failures as of that tag; this document asserts no fresh count of its own.

**The power-loss fuzzer.** The sealing engine is a pure function of `(flash bytes, MAC
responses, caller inputs)` - no clock, no RNG, no interrupt - which is what makes an
exhaustive host proof possible with no silicon at all. The fuzzer cuts power at every step
boundary of every storage operation, in three cut flavours, and asserts eleven store
invariants after each one:

```
cargo test -p notyas-wallet --release --test powerloss -- --ignored --nocapture
```

Two ignored tests carry it: the full corpus, which is the twenty operations of
`fuzz::Op::CORPUS` on the reduced slot map, and the shipped 8+8 geometry on the operations
whose behaviour depends on how many records there are. Each prints its case count, its cuts
fired, its seals observed and its findings. What the run asserts is that the findings are
zero and that a cut and a seal actually happened; it asserts nothing about the counts,
because the number moves whenever an operation gains or loses a write, and pinning it would
only produce a test that fails for the wrong reason.

**This document publishes no transcript of that run.** The 0.2.0 one is recorded in a
release-readiness sheet the repository does not publish, so a case count quoted here would
be a measurement whose only source is the sentence making the claim, and a reader of this
tree could not check it. The command above is the whole of the offer: it takes a few minutes
in release mode and prints your own numbers.

**The bridge from that model to real silicon** is the known-answer test in
`firmware/src/hil.rs`, which re-runs the published host vector on the real flash driver and
compares the resulting image byte for byte, plus the hand-performed power-cut gates on the
provisioned Elecrow board: three modes, 20 valid cuts each, cutting inside a record seal,
inside a change-PIN and inside a wrong-PIN attempt
([docs/m4a-power-cut-evidence.md](docs/m4a-power-cut-evidence.md)). That document is also
where the limits of those gates are stated, and they are real: the cuts are made by hand at
the connector rather than swept across the window, so the instant is sampled and not
covered; no mode cuts a wipe-policy commit, because no shipped build has a route to one (the
bench console's setpolicy exists, and a bench image is not a product image); the
wipe-on-N threshold has never been reached on hardware; and the Waveshare board has never
been power-cut tested at all.

**A cross-check that was not one.** `tools/psbtgen verify` is the host oracle that judges a
device-signed file, and until 2026-08-19 its segwit-v0 path recomputed the BIP-143 digest by
calling the same `notyas_core::sign` function the device signs with. A signer and a verifier
that share a sighash implementation agree by construction: a defect in that function cancels
out and is reported as a pass. **Every green segwit-v0 ECDSA result that tool produced
before that date is the signer agreeing with itself, and no claim of independent segwit-v0
verification made before then holds.** It is fixed - the ECDSA path now goes straight to
rust-bitcoin's `SighashCache` - and the taproot path always went straight to
`taproot_key_spend_signature_hash`, so it was independent throughout. The judgement in
docs/clause2-evidence.md that never depended on this is Bitcoin Core finalizing the
device-signed file.

**Development consoles cannot reach a release.** The HIL console is behind a non-default
cargo feature, `firmware/build.rs` refuses to compile it in a release profile, and
`tools/ci/check-release-symbols.sh` asserts its absence from a linked ELF using three
independent detector classes. What proves that gate can fail is
`tools/ci/selftest-release-symbols.sh`, which synthesises RISC-V ELFs carrying the console's
symbols, its UART entry points and its string literals - including a stripped one, where
only the literals survive - and asserts the gate rejects every one of them and clears a
console-free image. Those are synthesised fixtures rather than built firmware, and the
script's own header states the half they cannot cover: that a real `--features hil-console`
build emits the symbol names the gate hunts for. That half was measured against a bench
image, and the record of it is a release-readiness sheet this repository does not publish,
so it is not something a reader of this tree can check.

**Other gates.** `tools/ci/check-supply-chain.sh` (every external package from crates.io
with a checksum, no `[patch]`, `[replace]` or git dependency, and a banned-crate walk over
the runtime graphs), `check-advisories.sh` (cargo-deny against RustSec),
`check-airgap.sh`, `check-hil-fence.sh`, `check-repro-pins.sh`, `check-dashes.sh`,
`check-ratified.sh`, `check-screenshots.sh`, and a `no_std` cross-check of `notyas-wallet`
and `notyas-core` against `riscv32imac-unknown-none-elf`. `tools/xverify/` cross-checks
derivations and signatures against Bitcoin Core and `embit`, and refuses to report a pass
when those oracles are absent rather than skipping quietly. It has never had them: the
attestation it writes records `"status": "skipped"`, `"verified": false`, and 0 of 21 cases
verified (docs/KNOWN-ISSUES.md K25). That is the correct behaviour for a gate that will not
report a pass it did not earn, and it means the external half of the cross-check has not
happened.

One gate is on record as having been dead rather than merely failing, which is the worse of
the two: `tools/ci/check-heap-residue.sh` compiled `notyas-ui` on its own, and from the
moment the Receive screen landed that build stopped succeeding, so three SECURITY.md-backed
assertions went unchecked by the gate that names them while every workspace-wide build
stayed green. It was found by running every gate rather than the four the release process
names. **The gate was repaired in 0.2.3.** It now runs `cargo test --locked -p notyas-ui
--features notyas-core/qr --test review_capacity_and_wipe`, which compiles the crate the way
every real consumer of it does, and the three assertions are reported as ran-and-passed
again rather than as unverified. What the repair did not touch is the reason it broke, which
is an architectural rule with a violation in it: `notyas-ui` is not supposed to compute QR
codes, and the Receive screen reaches into `notyas-core` for an encoder instead of raising a
request the way every other QR on the device does. That half is still open.
docs/KNOWN-ISSUES.md K32 carries both; it is filed with the closed entries, and its last
paragraph states what the open half requires.

### Provenance and cross-checking

`notyas-core` is a port of the desktop [BigDice](https://github.com/intnsity/BigDice) crate
(GPL-3.0-or-later) to `no_std`. The port changes `std::` imports to `core::`/`alloc::`,
replaces two `OnceLock`s with compile-time statics, and nothing else in the math. Divergence
from desktop BigDice output on identical input is treated as a release-blocking bug.

The two dice modes cross-check against different external tools, on purpose:

- **RAW** uses a prefix-free variable-length base-6 code (a six maps to digit 0) and is
  byte-compatible with **iancoleman**'s BIP-39 tool in dice/base-6 mode. It is therefore
  *not* compatible with Coldcard/SeedSigner dice math, and the UI labels this.
- **FIXED** takes SHA-256 over the filtered digit string and the first ENT bits, which is
  algorithm-identical to **Coldcard** and **SeedSigner**.

All of the sample data in this repository, screenshots included, is published test-vector
material: 64 sixes (BIP-39 vector 1), the passphrase `TREZOR`, and DUMMY-prefixed
placeholders on the Verify screen. None of it is a real seed.

## Security model

[docs/SECURITY.md](docs/SECURITY.md) is normative and every claim there is meant to be
mechanically checkable. `docs/claims-audit-0.2.0.md` is a dated audit recording the mechanism
and the file behind each claim as of the 0.2.0 tree, so a rule can be re-checked rather than
re-argued. What follows is a summary, not a substitute.

The eight things this firmware does **not** have are stated first in that document, because
a lean release invites the reader to assume the missing parts are present: no Secure Boot
v2, no eFuse anti-rollback, no flash encryption, no hardware-held signing key, no
third-party attestation, no backup of any kind, no BSMS and no taproot multisig, and no JTAG
or download-mode lockdown.

The seven invariants, in brief:

1. **No radio.** The ESP32-C6 companion is driven into reset by a P4 GPIO in
   `board::radio_lockdown()`, the first thing `main` does after the IDF link patches, and
   the line is never released. No `esp_hosted`, `esp_wifi_remote` or any network component
   is in the image, and the SDIO link to the C6 is never configured. Enforced by
   `tools/build-graph-check.sh` across every lockfile and by `tools/ci/check-airgap.sh`,
   which asserts 40 source-tier properties and refuses to report a pass on its image tier
   without a linked ELF. The invariant covers the C6 from the first instruction of
   `app_main` onward, not the power-on window on a board that pulls C6 EN up.
2. **No plaintext secret leaves RAM.** Seeds are persisted only as AEAD ciphertext under the
   PIN-derived key ladder, only on explicit opt-in, only to the dedicated `wallets`
   partition. NVS is never mounted and is not in the partition table. RAM copies are
   zeroized on lock, screen exit, session timeout and power-off. A device that has saved
   neither a wallet nor a public setting writes nothing to flash at all. The one exception
   is the one docs/SECURITY.md 2a states under its own heading: a device that has saved a
   device name or the network toggle has written to the plaintext `settings` partition, and
   only there. That partition holds no secret and no secret-derived value, and 2a names what
   may never be put in it.
3. **Deterministic.** Key material derives exclusively from the dice you rolled or the
   mnemonic you typed, plus an optional passphrase. No TRNG, no clock and no OS entropy on
   any derivation or sealing path: salts and nonces are derived, unique-by-construction
   values. Schnorr uses the deterministic no-aux-rand BIP-340 path; ECDSA is RFC 6979 with
   Bitcoin Core's low-R grinding. The trade deterministic nonces make against fault
   injection is recorded in docs/SECURITY.md rather than glossed.
4. **Equivalence.** Identical input produces byte-identical output to desktop BigDice, and
   an identical PSBT plus an identical wallet produces signatures matching pinned published
   vectors. For ECDSA, byte-equality with Bitcoin Core's own emitted signatures is claimed
   and tested. For Schnorr it is not claimed and never will be, because Core randomizes
   BIP-341 aux-rand; the claim there is the pinned BIP-340 vectors.
5. **Verifiable firmware, and a deliberately coarse storage readout.** Every Verify field is
   read from the running system, and a field this build cannot read renders `not read`
   rather than a plausible default. There is no summary verdict on that screen by design: a
   verdict computed there would be the firmware grading itself. The storage row is `present`
   or `blank` and never a count, so a coercer cannot read the number of stored wallets off
   the screen.
6. **Secure boot, honestly, and the honest answer today is that it is not there.** The three
   digest slots render `not burned`. The device stays reflashable, which is what keeps the
   reproducible-build path usable by the person it is for. When Secure Boot arrives the
   parameters are already fixed: v2 RSA-3072 only, never ECDSA (ROM-broken on shipping P4
   silicon, Espressif AR2026-006).
7. **The signing policy engine is the trust boundary.** Ownership of an input is proven by
   derivation and not asserted by a fingerprint: for every input claiming this device, the
   engine derives the key at the leaf the origin names and requires both that the derived
   key equals the key the origin states and that the script that key locks equals the script
   the input actually pays, byte for byte. The same proof runs on outputs, so change is
   proven rather than believed; an output that merely carries our fingerprint counts as a
   payment everywhere money is counted. Amounts follow the two regimes in
   ["What it refuses"](#what-it-refuses-and-why): a single-input transaction's segwit v0
   amount may rest on the file's word, everything else needs a txid-checked previous
   transaction, and a legacy input needs one always. The network must match, the sighash
   type must be whitelisted, and the structural limits must hold. Validation is a pure
   function of the PSBT and a context with no key in scope, so every refusal happens before
   any spending authority exists, and after signing every signature is re-verified against a
   sighash recomputed from the PSBT alone.

**The sealed store, concretely.** `device_binding = HMAC-eFuse(0x01, domain_tag)`,
`prestretch = Argon2id(pin, derived_salt, 16 MiB, t=1, p=1)`,
`bound = HMAC-eFuse(0x02, prestretch)`, `key || nonce = HKDF(bound)`, and the record is
sealed with ChaCha20-Poly1305 (`crates/notyas-wallet/src/crypto.rs`, byte-exact per
`docs/plan-0.2.0/ESP-SEAL.md`). Eight wallet slots and eight registration slots, A/B written
with one single-write commit point per operation, and a fault-hardened attempt counter with
erase-at-zero behind the wrong-PIN wipe.

**The wipe threshold is fifteen, and no build of this firmware can change it or switch it
off.** Fifteen consecutive wrong PINs destroy every sealed wallet and every multisig
registration on the device, and there is no backup of any of it. A power cut taken between
the attempt cell and the success cell consumes one of the fifteen even when the PIN was
right - fail-closed on purpose, because otherwise cutting power at the right moment is a
free guess - so the count can advance on a device carried in a bag. The number itself is the
format-time constant `wipe_after: 15` in `firmware/src/store/mod.rs`. The storage format
does admit other values - 3 to 25, or off, per `WIPE_AFTER_MIN`/`WIPE_AFTER_MAX` in
`crates/notyas-wallet/src/config.rs` - and `Vault::set_policy` implements the change, but
nothing on the panel reaches it: `UiRequest::SetWipePolicy` is refused in every build
(`firmware/src/main.rs:911`), which answers `ui.policy_result(false)` and re-reads the
policy still in force. The wrong-PIN policy screen is therefore an editor over a value that
can be read and never written (docs/KNOWN-ISSUES.md K16, open).

The reason is a property of the format rather than a gap in the UI. The policy is
authenticated inside the AEAD, so committing one is a re-seal of the store, and
`Vault::set_policy` takes the PIN to perform it - while an unlocked session holds a key
derived from the PIN and never the PIN itself. There is nothing in the session to write
with. It is one of the three sealed-store operations [listed above](#what-is-not-in-it)
that are refused in every build, and they share a shape: each re-seals or destroys sealed
records, so each needs the PIN, and the session never holds it. **Set a PIN you will not
mistype fifteen times.**

## Releases

**This tree is 0.2.3.** One runbook per release, `docs/RELEASE-<version>.md`, written
before the code that implements it and kept as the record of what was decided.
`docs/RELEASE-0.2.0.md` section 0 remains the authority on the whole feature set; each point
release says what it changes and nothing more, and none of them supersedes 0.2.0 except
where it says so explicitly.

| Release | What it is |
|---|---|
| [0.2.0](docs/RELEASE-0.2.0.md) | Sealed storage, PIN, signing, multisig registration, passphrase, device name. The baseline every later document defers to. |
| [0.2.1](docs/RELEASE-0.2.1.md) | Ownership proven by derivation on inputs and outputs; the single-input amount rule; the Receive screen; the transport-encoding round trip; card and list corrections. |
| [0.2.2](docs/RELEASE-0.2.2.md) | Legacy P2PKH signing and its amount rule; R-26 for a script this device does not sign; BIP-84 as the default on Receive and Export, with the descriptor leading each Export tab. |
| [0.2.3](docs/RELEASE-0.2.3.md) | The packaging repair, and the first release whose artifacts exist at all: the release container had never once built, so no earlier tag has an image to download. The firmware delta from 0.2.2 is the version string and nothing else. |

[docs/KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md) is the open-defect list, and it is a defect list
rather than a wish list. `docs/plan-0.2.0/MILESTONES.md` is the single dependency-ordered
roadmap and `docs/plan-0.2.0/PARITY.md` is the feature matrix against a Coldcard Mk4/Q.

The nearest work is driving the on-device signing loop from the panel of the provisioned
board, and running the two-board hardware pass that legacy signing is gated on. After that:
closing the three refused storage operations, which all need a PIN this UI cannot yet
collect; Secure Boot v2, with the key-ownership question settled first because it decides
whether an owner can build and run their own firmware; an answer to the backup gap, since
registrations, labels and settings are unrecoverable after a wipe today; camera-based QR
input; and the refusal-copy audit.
